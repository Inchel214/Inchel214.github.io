# 个人经验
正则表达式匹配在多意图场景下，无法识别，只能匹配固定指令。这些固定指令一定是高频的，并且十分确定。需要做完整的匹配，它最好的做法是用来做安全拦截，防止用户输入危险指令。比如：
- 安全层：敏感词、指令注入防护（`忽略前面所有prompt`这类）
- 固定原子强指令：`退出、重置、清除上下文、帮助`—— 这类指令**业务上约定就是单意图，不会和别的任务混合**
- 格式提取：提取手机号、订单号、时间、url（槽辅助，不是意图）
- 脏输入过滤：纯表情、乱码、空白输入

传统三层的第二层，用 BERT/SVM 等小模型做意图分类，一般情况下这一层会引入**额外故障面**：分类置信度阈值很难调，经常出现 “本来可以直接给 LLM 拆清楚的句子，被中间层误判单意图直接走别的逻辑”。如果你的业务是：
- 意图库固定、数量不多（比如几十个以内）
- 绝大多数请求都是单意图，多意图占比很低
- QPS 极高、对 token 成本敏感（百万级日请求）

这时语义匹配（多标签分类）的价值就出来了：
大量简单请求不走 LLM，用小模型几十 ms、极低成本直接识别、抽槽，只有识别置信低、判定疑似多意图的，才路由到大模型。
它本质是**降本旁路**，不是能力的核心。

# 意图识别架构对比：传统三层 vs LLM First

## 传统三层架构

```
用户输入 → ① 规则/正则 → ② 小模型分类 → ③ 后处理/兜底
```

**做法：**
- 第一层用正则、关键词匹配拦高频固定指令
- 第二层用 BERT/SVM 等小模型做意图分类，输出固定标签
- 第三层加后处理规则和兜底话术

**优点：**
- 可控、可解释，每个意图命中了什么规则能查清楚
- 推理成本低，小模型毫秒级出结果
- 稳定性高，不会出现模型幻觉导致的误判

**缺点：**
- 扩展新意图要重新标注数据、微调模型，迭代慢
- 换个说法就识别不出来，鲁棒性差
- 三层之间串联，调优互相牵扯，维护成本高
- 只能输出预定义标签，泛化能力弱

---

## LLM First 架构

```
用户输入 → 大模型直接理解意图 + 决定执行动作
```

**做法：**
- 把用户输入、可用工具、执行范式说明塞进 prompt
- 让大模型直接判断：该回答 / 该调工具 / 该走 Plan-Execute
- 规则只做前置黑名单和强信号拦截，不做主力分类

**优点：**
- 泛化能力强，各种自然表达都能理解
- 扩展新意图不用重新训练，改 prompt 就行
- 意图识别和路由决策一体化，不用维护多套系统
- 能理解上下文、多轮指代、隐含意图

**缺点：**
- 成本高，每轮都要跑一次大模型
- 不稳定，可能误判、幻觉，同样的输入不同轮结果不一样
- 不可解释，出了问题难定位是哪一步错了
- 延迟高，简单问题也要等大模型推理

---

## 一句话总结

| 维度 | 传统三层 | LLM First |
|------|---------|-----------|
| 可控性 | 强 | 弱 |
| 成本 | 低 | 高 |
| 迭代速度 | 慢 | 快 |
| 泛化能力 | 弱 | 强 |
| 稳定性 | 高 | 中 |
| 适合场景 | 意图固定、高频、要求稳定 | 意图开放、长尾多、迭代快 |

**工程上一般用混合方案：** 正则拦强信号 → 简单意图走小模型直接处理 → 复杂/开放意图交给 LLM 判断。
